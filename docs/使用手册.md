# AI Opportunity Radar — 使用手册

> **一句话**:每天早上自动从互联网 7 个数据源拉 AI 相关信号 → LLM 筛选 → 评分 → 深度研究 → 自动生产销售文案(Telegram / 闲鱼 / 小红书),**你的代码不是商品,你的代码是生产商品的机器**。

> **v2.0 改造目标**(见 [`继续文档.md`](继续文档.md)):
> 放弃 SaaS 化,聚焦"内容生产 + 多平台分销"。系统每天自动生产 10+ 条可销售内容,通过闲鱼 / 小红书 / 公众号 / 飞书完成销售,90 天内验证第一笔收入。

---

## 一、项目是什么

**AI Opportunity Radar v2.0** 是一个自托管的 **AI 商业情报生产系统**,每天 02:00 UTC 自动跑一遍完整流程,从公开互联网发现并评估 AI 产品机会,然后**自动生成可销售的内容**(不只是"通知"):*长文日报*(飞书/公众号)、*闲鱼商品 listing*、*小红书笔记*。

**完整流程**:
```
互联网 7 个数据源
  ↓ 抓取
RawItem(原始素材)
  ↓ LLM 筛选(MiniMax-M3)
Signal(有效信号)
  ↓ 确定性公式打分
Opportunity(0-100 分,带 8 个商业字段)
  ↓ 深度研究(LLM + Firecrawl + Browser Use)
ResearchReport(报告)
  ↓ 内容生成器(Phase 1 v2.0 新增)
   ├─ daily_report     → Markdown 长文 → 飞书 / 公众号
   ├─ xianyu_product   → JSON 商品    → 闲鱼(手动复制发布)
   └─ xiaohongshu_post → Markdown 笔记 → 小红书
  ↓ 飞书机器人推送(Phase 2 v2.0 新增)
   └─ 每日 02:30 UTC 自动推送日报卡片到飞书群
```

**6 个数据源**:`github` / `reddit` / `hackernews` / `producthunt` / `rss` / `youtube`

**回退链**:`Browser Use` → `Firecrawl` → `Mock`(任何一个挂了,自动降级到下一个,系统永远可用)

**8 个商业字段**(v2.0 新增在 `opportunities` 表):
- `target_customer` — 目标客户画像(企业级用户描述)
- `market_size` — 市场规模量级(如 `100M-500M USD`)
- `mvp_days` — 单人 MVP 估算天数
- `difficulty` — 实现难度(`easy` / `medium` / `hard`)
- `monetization_model` — 商业模式(如 `SaaS 订阅 49 USD/月`)
- `china_gap` — 中国市场空白点
- `content_status` — 内容生命周期(`new` → `generated` → `published` → `sold`)
- `commercial_status` — 销售资格(`unqualified` → `qualified` → `promising`)

### 步骤 1:克隆项目(假设已 clone,跳过)

### 步骤 2:填配置文件

```bash
cd /Users/jiang/development/AI\ Opportunity\ Radar
cp .env.example .env
```

打开 `.env`,**必须**填这几个(其他可以保持默认):

MINIMAX_API_URL=https://api.minimaxi.com/anthropic

# Telegram(必填,否则收不到推送)

# 网页抓取(至少一个,推荐两个都填)

# n8n(可选,但推荐)

```bash

### 步骤 5:登录 n8n(只第一次)

打开 http://localhost:5678,用:
- Email: `admin@radar.local`
- Password: 你 `.env` 里设的 `N8N_PASSWORD`

### 5.3 n8n 面板(http://localhost:5678)

4 个工作流:

| 工作流 | 触发方式 | 干什么 |
|---|---|---|
| `daily-opportunity-discovery` | **每天 02:00 UTC 自动** | 6 步全流程:发现 → 聚类 → 筛选 → 评分 → 研究 → 推送 Telegram |

## 五之二、v2.0 内容生产工作流(核心商业能力)

> **这是 v2.0 的核心价值** —— 上一节讲的是"看机会",这一节讲的是**自动产出可销售内容**。

### 5 个内容生成器

| 生成器 | 输出 | 销售渠道 | 用途 |
|---|---|---|---|
| `daily_report` | Markdown 长文 | 飞书机器人 / 公众号 | 完整日报,有标题/来源/痛点/市场/机会/行动 6 个固定章节 |
| `xianyu_product` | JSON 商品 listing | 闲鱼(手动复制发布) | 自动生成 ¥39-¥99 的数字商品,3-5 条卖点 + 定价建议 |
| `xiaohongshu_post` | Markdown 短文 | 小红书 | 300-600 字爆款笔记,带话题标签 + CTA 占位符 `{{CTA_URL}}` |

每个生成器:
- 输入 = `Opportunity` + 深度研究 `ResearchReport` + LLM Provider
- 输出 = `GeneratedContent`(标题 / 格式 / 内容 / 元数据 / 时间戳)
- 同时落库到 `notifications` 表(`channel` 字段对应销售渠道)

### 手动触发内容生成

```bash
# 跑 Top 5 的所有生成器
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"limit": 5, "only_qualified": true}'

# 指定具体的机会 ID
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"opportunity_ids": [12, 34, 56]}'

# 只跑某个生成器
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"limit": 3, "generators": ["xianyu_product"]}'

# 跳过未达标的
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"limit": 10, "only_qualified": false}'
```

> **关于 `X-Radar-Webhook`**:虽然 env 变量叫 `RADAR_WEBHOOK_SECRET`,但后端 `_check_webhook_secret()` 优先用 `APP_SECRET_KEY`(回退到 `RADAR_WEBHOOK_SECRET`)。生产建议两者都设置成同一个长随机串。

返回示例:
```json
{
  "generated_count": 15,
  "error_count": 0,
  "enriched_count": 5,
  "errors": []
}
```

### 查看已生成的内容

```bash
# 列出最近 50 条生成记录(按 channel 过滤)
curl 'http://localhost:8000/api/internal/notifications/history?limit=50&channel=xianyu' \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>"
```

返回的每条 `payload` 字段就是完整的 GeneratedContent,可以解析后直接复制到对应平台。

### 扩展:加新的内容生成器

只需要:
1. 在 `backend/app/services/content_generator/` 下新建一个文件,实现 `ContentGenerator` ABC
2. 文件末尾调用 `register(MyGenerator())` 自注册
3. 容器重启(开发模式 `--reload` 自动生效)

不需要改任何已有文件。

## 五之三、飞书机器人(Phase 2 v2.0)

> 这是 v2.0 的**企业情报交付通道** —— 每天早上 02:30 UTC 把昨日评分最高的 5 个机会打成一张交互式卡片,推到飞书群。

### 配置飞书自定义机器人

1. 在飞书群里,**设置 → 群机器人 → 添加机器人 → 自定义机器人**
2. 选"自定义机器人",设个名字,**关键:打开"加签"安全设置**(可选,推荐打开)
3. 复制 **Webhook URL**(形如 `https://open.feishu.cn/open-apis/bot/v2/hook/<token>`)
4. 如果开了加签,复制 **签名校验 secret**
5. 填进 `.env`:

```bash
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxx
FEISHU_WEBHOOK_SECRET=你的加签 secret  # 留空 = 不签名
FEISHU_TIMEOUT=15.0
```

6. 重启后端:
```bash
docker compose restart backend
```

### 自动推送

每天 02:30 UTC(主流程 02:00 UTC 跑完后 30 分钟),n8n 自动调用:
- 工作流:`feishu-daily-digest`
- 调后端:`POST /api/internal/feishu/digest/send`

如果飞书 webhook 没配,后端自动降级到 mock provider,**不会报错**,测试时也能照常触发。

### 手动触发

```bash
# 立即推一次日报(默认最近 24 小时 Top 5)
curl -X POST http://localhost:8000/api/internal/feishu/digest/send \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"limit": 5, "only_qualified": true, "window_hours": 24}'

# 全历史 Top 10(给潜在客户演示用)
curl -X POST http://localhost:8000/api/internal/feishu/digest/send \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"limit": 10, "window_hours": null}'

# 自动先跑内容生成器再推送(确保卡片背后的内容已落库)
curl -X POST http://localhost:8000/api/internal/feishu/digest/send \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"limit": 5, "auto_generate_content": true}'
```

返回示例:
```json
{
  "sent": true,
  "opportunity_count": 5,
  "window_start": "2026-08-26T12:30:00+00:00",
  "window_end":   "2026-08-27T12:30:00+00:00",
  "error": null,
  "provider": "feishu",
  "body_chars": 1823,
  "content_generated": 5

```

### 加签模式

如果飞书群机器人开了"加签",后端会在 body 里自动附加:
```json

  "msg_type": "interactive",
  "card": {...},
  "timestamp": "1700000000",

}
```
算法在 `backend/app/services/feishu/base.py:sign_feishu_payload()`,有完整测试覆盖,匹配飞书官方参考实现。

## 五之四、Content Center 内容生产中心(Phase 3 v2.0)

> **这是一个 UI 工作台** —— 把内容生产器(Phase 1)和飞书推送(Phase 2)产生的内容**集中到一个页面**,让人可以一眼看到每个机会对应 4 个渠道的销售文案,并跟踪发布/成交状态。

### 打开

http://localhost:3000/content-center

### 它长什么样

每个高分机会一行,从左到右 4 张卡片(对应 4 个销售渠道),顶端有状态徽章和两个操作按钮:

```
┌─────────────────────────────────────────────────────────────────────┐
│ AI 法律合同审核                                  [✓ 已发布]          │
│ 评分 87.5 · 商业 qualified · 市场 100M-500M USD · MVP 14 天         │
│ 中国空白:中国律所市场分散,微信小程序是关键渠道                      │
│                                                  [标记已发布] [标记已售出] │
├──────────────┬──────────────┬──────────────┬──────────────────────┤
│ 飞书         │ 闲鱼         │ 小红书        │ 公众号                │
│ ┌──────────┐ │ ┌──────────┐ │ ┌──────────┐ │ ┌──────────────────┐ │
│ │ # 今日AI │ │ │ ¥49      │ │ │ 国外一个 │ │ │ 尚未生成。          │ │
│ │ 商业机会 │ │ │ 100 个AI │ │ │ AI 月入 │ │ │ 先到 n8n 触发     │ │
│ │ ...      │ │ │ 机会     │ │ │ 5 万美元 │ │ │ 内容生产。          │ │
│ └──────────┘ │ └──────────┘ │ └──────────┘ │ └──────────────────┘ │
│  [复制]      │  [复制]      │  [复制]      │                       │
└──────────────┴──────────────┴──────────────┴──────────────────────┘
```

### 4 个渠道

| 渠道 | 内容格式 | 用途 |
|---|---|---|
| **飞书** | Markdown 长文(完整日报) | 飞书群里看的机会情报 |
| **闲鱼** | JSON listing(标题/价格/卖点) | 数字商品,¥39-¥99 自动定价 |
| **小红书** | Markdown 短文(300-600 字) | 笔记风格,带话题标签 |
| **公众号** | Markdown 长文(预留位) | 1 周 / 1 月复盘型深度文章 |

### 操作流程

1. **看** — 系统每天 02:00 UTC 跑完发现流程后,**自动**跑内容生成器生成所有 4 个渠道内容(由 Phase 1 的 `/api/internal/content/generate` 端点触发,通常在 n8n `daily-opportunity-discovery` 末尾)
2. **复制** — 点卡片右上角"复制"按钮,内容到剪贴板,粘贴到对应平台发布
3. **标记已发布** — 发布到任意平台后,点"标记已发布"按钮,系统把 `content_status` 从 `generated` 改成 `published`
4. **标记已售出** — 真正卖出商品(闲鱼成交、付费阅读、订阅等)后,点"标记已售出"按钮,系统把 `content_status` 改成 `sold`,并把 `commercial_status` 升级为 `promising`

### 状态机

```
new (尚未生成)
  ↓ n8n 跑内容生成器
generated (已生成,可复制)
  ↓ 用户点"标记已发布"
published (已发布到外部平台)
  ↓ 用户点"标记已售出"
sold (已成交)  →  用于统计 ROI
```

每次状态变化都走后端,前端只是显示。状态变化会自动同步到:
- Dashboard 统计卡片
- Telegram / 飞书 每日推送(高亮已售出机会)
- `notifications` 表(留痕审计)

### 过滤参数

URL 上加参数:
```
/content-center?only_qualified=false&limit=50
```
- `only_qualified` — 默认 `true`,只显示 `commercial_status=qualified` 的高潜机会。改成 `false` 看全部。
- `limit` — 默认 20,最多显示多少行机会。

### 手动触发生成内容

如果想**立刻**给某些机会生成内容(不等 n8n 凌晨):
```bash
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"limit": 10, "only_qualified": true}'
```
然后刷新 Content Center 页面,新内容就出现了。

| GET | `/api/internal/content/by_opportunity` | 列出每个机会的最近一份各渠道内容 |
| POST | `/api/internal/content/{opportunity_id}/mark_published` | 把机会标记为已发布 |

```

### 为什么不用 Tiptap / Notion 那种富文本编辑器?

**故意保持简单**。Content Center 只做三件事:看、复制、改状态。富文本编辑器需要数据库 schema 迁移、协同锁、版本控制,这些都不是 v2.0 的商业价值(90 天第一笔收入)。复制到外部平台用平台自己的编辑器发布,反而避免重复维护。

## 五之六、按需深度研究报告(Phase 5 v2.0)

> v2.0 的 **Product 2:AI 创业分析服务**(¥299-¥999/份)。客户付钱后,运营者输入一个公开 URL 或一个主题,系统会用与日常流水线**完全相同**的抓取 + LLM 流程即时生成七段式研究报告,并把销售作为订单登记 —— 全程一次 HTTP 调用完成。

### 设计动机

日常的"discovery → screening → scoring → research"流水线是**主动的**:每天 02:00 UTC 跑一次,从公开互联网里*发现*机会。按需报告是**被动的**:客户点名要看某个项目,我们要*立即*给一份同等深度的分析。

实现上:
1. 用客户的输入(URL 或主题)直接生成一个**临时 Opportunity**(slug = `on-demand-<uuid16>`)。
2. 把这个 URL/主题作为 **seed URL** 传给 `ResearchService.process_job(seed_urls=...)` —— **不**走发现→筛选打分那条慢路。
3. 走与日常流水线完全相同的:抓取 → LLM 七段式合成 → 落库 `research_reports`。
4. 如果请求里带了客户信息,**同一调用**创建 Order 并把机会标记为 `content_status='sold'`、`commercial_status='promising'`。

### 入口

| 名称 | 路径 | 说明 |
|---|---|---|
| **On-demand** | `/on-demand` | 输入 URL 或主题,生成报告;同时登记订单 |

顶部导航的 **On-demand** 入口直达。

### API

```bash
# 1. URL 模式:生成报告
curl -X POST http://localhost:8000/api/internal/research/on_demand \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/ai-product"}'

# 2. 主题模式:系统会先用主题搜索种子 URL,再开始研究
curl -X POST http://localhost:8000/api/internal/research/on_demand \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"topic": "AI 法律合同审核"}'

# 3. URL + 客户信息:一次调用同时生成报告 + 登记订单(¥299)
curl -X POST http://localhost:8000/api/internal/research/on_demand \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/paid-report",
    "customer_name": "李四",
    "customer_contact": "wechat:lisi",
    "amount_cny": 299,
    "channel": "wechat",
    "payment_method": "wechat",
    "notes": "first paid report"
  }'

# 4. 最近任务列表(默认 20 条)
curl -s "http://localhost:8000/api/internal/research/on_demand/recent?limit=20" \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>"

# 5. 单份报告完整详情(含全部 7 段 + 来源)
curl -s "http://localhost:8000/api/internal/research/on_demand/7" \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>"
```

#### 请求体约束(`OnDemandResearchRequest`)

- `url` 和 `topic` **二选一**,不能同时给也不能同时不给。
- URL 模式:只填 `url`,后端用它直接抓取。
- 主题模式:只填 `topic`,后端先用主题在 WebDataProvider 上做 search,拿到的 URL 作为 seed。
- 订单字段:**任何**一个客户/支付字段被设置,`customer_name` 和 `amount_cny` 都必填(其他字段:contact / channel / payment_method / payment_reference / notes 都可选)。

#### 响应体(`OnDemandCreateResponse`)

```json
{
  "opportunity_id": 100,
  "opportunity_title": "https://example.com/ai-product",
  "opportunity_slug": "on-demand-a1b2c3d4e5f6g7h8",
  "job_id": 7,
  "status": "completed",
  "recommendation": "recommend",
  "confidence": 0.78,
  "sources_count": 3,
  "executive_summary": "…",
  "order_id": 88
}
```

注意:接口是**同步**返回 —— 报告生成完才回包。如果怕超时,后续 Phase 可以拆成 `job_id` 异步模式。

### 前端页面(`/on-demand`)

1. **种子切换**:URL / 主题。
2. **可选附加订单**:`同时记录一笔订单` 复选框 —— 勾选后展开客户、联系方式、销售渠道、金额、备注字段。
3. **生成报告**:点击后内联展开七段式报告(执行摘要、市场分析、竞争分析、中国市场分析、变现分析、MVP 分析、风险分析)+ 参考资料链接。
4. **最近任务**:下方表格按时间倒序列出所有按需生成的任务,带推荐、置信度、来源数、状态徽章。

### 与日常流水线的关系

| | 日常流水线 | 按需报告 |
|---|---|---|
| 触发 | n8n 02:00 UTC 自动 | 运营者手动(UI/API) |
| 种子来源 | RawItem / OpportunitySource | 客户输入的 URL 或主题 |
| Opportunity 来源 | discovery → screening → scoring | 直接 bootstrap 一个 `(on-demand)` slug |
| Research 流程 | 完全相同 | 完全相同(`seed_urls` 覆盖) |
| 订单 | 不产生 | 可选,同一调用创建 |
| `content_status` | generated / published / sold | 生成后直接 → sold(若带订单) |

### 关键设计取舍

- **复用 `ResearchService` 而不是写一份新的**:任何抓取/LLM 流程的 bug fix 都自动惠及按需路径。代价是 `process_job` 多了一个 `seed_urls` 参数 + `_gather_sources` 一个 if 分支,极少侵入。
- **同调用创建订单**:运营者在客户付款后只点一次"生成报告"。`order_id` 在响应里直接返回,UI 也能立刻高亮&ldquo;订单 #88 已登记&rdquo;。
- **slug 带 `on-demand-` 前缀**:让 `GET /research/on_demand/recent` 能用 `Opportunity.summary LIKE '(on-demand)%'` 一句话过滤,不需要在表上加 `kind` 列。
- **不写新表**:`ResearchJob` + `ResearchReport` + `Order` 三张现有表已经覆盖所有需求。`on-demand` 只是一个 bootstrap 模式,不是一个新实体。

## 五之七、飞书智能助手(Bot 抽象层 + 双向交互,Phase 6 v2.0)

Phase 2 实现了飞书**出站**日报推送(自定义机器人 Webhook)。Phase 6 把这件事升级成**飞书智能助手**:

1. **架构层**:抽出 `BotProvider` 接口,Telegram / Feishu 共用同一份调用契约,`NotificationService` 不再写死 Telegram。
2. **容错层**:飞书推送失败时**自动降级** Telegram(可配置)。
3. **交互层**:接收飞书**事件订阅**回调,把用户在群里的命令(`/today`、`/research AI 法律合同` 等)路由到现有内部 API。

> **本地零配置**:Phase 6 完全支持离线 mock 跑通 — 不需要公网 HTTPS、不需要真实飞书 App 注册。部署到生产时再补飞书开放平台凭证和 ngrok / 反向代理。

### 设计动机

之前的痛点:

- 同一份"每日 Top 5"内容要走两条不同的代码路径才能推两份(Telegram + 飞书)
- 任何内容格式调整都得改两处
- 群里用户问"今天有什么机会?"**没人接** — 因为只有出站没有入站

Phase 6 的解决方案:

- **抽 `BotProvider`**:Telegram / Feishu 各自提供一份 adapter,统一对外暴露 `send(target, message) -> BotSendResult`
- **抽 `FallbackBotProvider`**:primary 失败 → secondary 兜底,运营场景下"飞书挂了我们也得有一条信号出去"
- **抽 `FeishuCommandRouter`**:每条命令只是**路由**到现有 internal API(`/api/internal/research/on_demand` 等),**不重复业务逻辑**

### 命令清单

所有命令都在飞书群里 **@机器人** 触发(也支持私聊)。机器人返回飞书卡片,直接在群里可见。

| 命令 | 作用 | 路由到 |
|---|---|---|
| `/help` | 命令菜单 | 静态卡片 |
| `/today` | 今日 Top 10 机会 | `GET /api/opportunities?limit=10` |
| `/top` | 全历史 Top 10 | `GET /api/opportunities?limit=10` |
| `/research <主题>` | 按需生成研究报告(¥299 场景) | `POST /api/internal/research/on_demand` |
| `/refresh` | 触发数据抓取 | `POST /api/internal/discovery/run` |
| `/score` | 触发重新评分 | `POST /api/internal/scoring/run` |
| `/daily` | 触发日报推送(主通道 → 降级) | `POST /api/internal/notifications/digest/send` |
| 任意文本 | 命令解析失败 | 提示用户试 `/help` |

中文别名同样支持:`/今日` `/分析` `/刷新` `/重评` `/日报`。

### 推送通道选择 + 容错降级

新增 `.env` 配置:

```bash
# 主推送通道: feishu (国内可达 + 知识库 + 权限) | telegram
NOTIFICATION_DEFAULT_CHANNEL=feishu
# 失败时降级顺序: CSV。失败一个就试下一个,首个成功的为准
NOTIFICATION_FALLBACK_CHANNELS=telegram
```

`FallbackBotProvider` 的语义:

- `primary.send(...)` 返回 `ok=False` → 自动调 `secondary.send(...)` 同一 `BotMessage`
- `primary.send(...)` 抛 `ExternalServiceError` → 同上
- **重试次数 = 1**(不无限重试;运营场景下重试只会复现同一个 bug)
- 双双失败 → 返回 `ok=False` 的 `BotSendResult`,`error` 字段同时记录两个 provider 的失败原因(`primary=feishu-adapter failed[...]; secondary=telegram-adapter failed[...]`)
- 每次失败都打 `record_external_error(provider, kind)` Prometheus 指标

合并后的 `/api/internal/notifications/digest/send` 现在支持 `channel` 字段:

```bash
# 默认 = settings.notification_default_channel = feishu
curl -X POST http://localhost:8000/api/internal/notifications/digest/send \
  -H "X-Radar-Webhook: $APP_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"channel": "feishu"}'

# 临时切到 Telegram
curl -X POST http://localhost:8000/api/internal/notifications/digest/send \
  -H "X-Radar-Webhook: $APP_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"channel": "telegram"}'
```

### 入站事件接收

新挂载的路由:

```
POST /api/feishu/event   ← 飞书开放平台 事件订阅 回调地址
```

处理三种入站形态:

| 形态 | body 示例 | 处理 |
|---|---|---|
| URL verification(握手) | `{"challenge": "..."}` | 原样回 `{"challenge": "..."}` |
| 无加密消息事件 | `{"header": {...}, "event": {...}}` | 解析 + 路由命令 + 返回卡片 |
| 加密事件(`{"encrypt": "..."}`) | (Phase 6.x stub) | 返回 `{}` 让飞书停止重试 |

签名验证用飞书自己的 `Verification Token`(body 的 `token` 字段),**不**走 `_check_webhook_secret`(那是 n8n → 后端的共享密钥,出站用的)。本地 mock 模式下 `feishu_verification_token` 留空 → 自动跳过签名校验。

## 五之八、飞书内容生态(云文档 + 多维表格,Phase 7 v2.0)

Phase 6 让机器人可以 **聊天**(收命令 + 回卡片)。Phase 7 把机器人升级成 **内容发布渠道**:研究 → 飞书云文档,机会 → 飞书多维表格 — 让用户在飞书里就能搜索 / 筛选 / 归档 / 二次消费,不再依赖聊天记录。

### 设计动机

之前的痛点:

- 研究报告只能在 `/on-demand` Web 页面看,生成完一次就过去了
- 每天的 Top-N 机会推一次就消失了,没法跨日对比、没法批量导出
- 群消息沉淀成本低(刷过去就没了),商业化产品需要 **东西** 而不是只有消息

Phase 7 的解决方案:

- **`/research` → 自动写云文档**:报告生成完立刻落一份 Docx 到飞书云盘
- **`/daily` → 同步多维表格**:Top-10 机会写入多维表格,可在飞书里筛 / 排序
- **`/report <job_id>`**:把过去任意一份已完成报告推到云文档(share)
- **`/table`**:手动一次性同步全表,适合初次接入时"灌库"

### 新增命令

| 命令 | 作用 | 副作用 |
|---|---|---|
| `/report <job_id>` | 把已完成的研究报告推到飞书云文档 | 写入 Docx,返回文档 URL |
| `/doc <job_id>` | `/report` 的别名 | 同上 |
| `/文档 <job_id>` | `/report` 的中文别名 | 同上 |
| `/table` | 把机会表(最多 200 条)同步到 Opportunities 多维表格 | 写入多维表格,返回 URL |
| `/表格` | `/table` 的中文别名 | 同上 |
| `/research <主题>` *(升级)* | 现在报告生成完会自动写一份云文档 | chat 回复里追加 `📄 [飞书云文档已生成]` |
| `/daily` *(升级)* | 触发日报推送 **并** 同步 Top-10 到多维表格 | chat 回复里追加 `📊 [今日 Top N 已同步]` |

### 新增环境变量

```bash

# 飞书多维表格 — Opportunities 专表(/table 手动同步)

### 飞书开放平台新增权限

在 [飞书开放平台](https://open.feishu.cn) 的 App → 权限管理 → API 权限里勾选下表的"权限名称"(显示名)。搜索框输入中文显示名就能找到 — 用 `docs:docx` 这种内部 scope 名是搜不到的。

| API 接口 | 权限名称(中文显示名) | Scope 标识符 |
|---|---|---|
| `POST /drive/v1/import_tasks`(markdown → Docx) | **查看、创建云文档导入任务** | `docs:document:import` |
| `POST /drive/v1/import_tasks` 备选 | 查看、评论、编辑和管理云空间中所有文件 | `drive:drive` |
| `POST /bitable/v1/apps`(创建多维表格) | **查看、评论、编辑和管理多维表格** | `bitable:app` |
| `POST /bitable/v1/apps/{token}/tables`(新增数据表) | 新增数据表 | `bitable:app:table` |
| `POST /bitable/v1/apps/{token}/tables/{tid}/records/batch_create`(批量新增记录) | 新增记录 | `bitable:app:record` |

**关键点 1**:`bitable:app` 一项覆盖所有 Bitable 操作(create app / table / record / update / delete) — 不需要分别勾 `*:readonly`。
**关键点 2**:搜不到 `docs:docx / docs:docx:readonly / bitable:table / bitable:table:readonly / bitable:record` — 这些不是当前 open-platform UI 里的可见 scope,**用中文显示名搜**。

然后在 **版本管理与发布** 页发一版新版本,飞书侧才会真的放行这些 API。

### 自动创建 vs 复用

`feishu_bitable_app_token` 和 `feishu_bitable_opportunities_app_token` 留空时,**首次使用自动创建**多维表格 App,新 `app_token` 通过 `feishu_bitable_app_created` 日志输出:

```log
feishu_bitable_app_created
  table_name=Opportunities
  app_token=BITAbcd1234567890
  hint="persist this app_token to .env (FEISHU_BITABLE_OPPORTUNITIES_APP_TOKEN)
        to avoid recreating on restart"
```

**强烈建议**:首次创建完把 token 复制回 `.env`,避免每次重启都新建一份多维表格(Bitable 不允许同名 App 在同一飞书租户下重复创建,会失败)。

### 排查清单

| 现象 | 可能原因 | 排查 |
|---|---|---|
| `/report 5` 回复"未配置" | `FEISHU_DRIVE_ROOT_FOLDER_TOKEN` 为空 | 在 `.env` 填入,重启后端 |
| `/report 5` 回复"文档创建失败:…quota" | 飞书租户云盘配额满 / 没有写权限 | 检查飞书企业版配额 + App 权限 |

| 第一次 `/daily` 后 Bitable 数据看得到,但 .env 没 token | 没读日志里的 `feishu_bitable_app_created` | `docker compose logs backend \| grep feishu_bitable_app_created`,复制 token 写回 |
| Docx 内容是 markdown 原文,没有飞书原生样式 | Phase 7 把 markdown 当原文喂进去 | 这是预期的 — 飞书 Docx 支持 Markdown 导入,会自动渲染标题 / 列表;如要自定义样式后续可以加自定义模板 |
| Docx 中文乱码 | 几乎不会发生(我们走 base64 + UTF-8) | 检查 `app/services/feishu/content_client.py:_DEFAULT_POLL_INTERVAL_SEC` 下面 `_render_report_markdown` 是否仍是 UTF-8 |

## 五之九、微信公众号 + 多渠道运营配套(Phase 8 v2.0)

Phase 8 把 Content Center 的 4 个渠道补齐(微信公众号空缺最久),并补了 5 个运营真正会需要的能力 — 一个 PR 一起做,比分两次 review 成本低。

### 4 个渠道的内容生成器差异表

| 渠道 | 字数 | 视角 | 标题规则 | CTA | 文件 |
|---|---|---|---|---|---|
| **daily_report**(飞书日报) | 600-1200 | 第三人称客观简报 | 模板化 `今日AI商业机会:X` | 无 | `daily_report.py` |
| **xianyu_product**(闲鱼) | JSON payload | 商品列表 | 标题 30 字以内,含价格 / 交付形式 | `微信:xxx` | `xianyu_product.py` |
| **xiaohongshu_post**(小红书) | 200-600 | 第一人种草 | emoji 钩子 | `#标签` + `评论领资料` | `xiaohongshu_post.py` |
| **wechat_article**(公众号,Phase 8 新增) | **1500-3000** | **第一人称故事化** | **14-26 字,数字钩子** | **文末三件套 `{{WECHAT_QR}}` / `{{WECHAT_ID}}` / `{{KNOWLEDGE_PLANET_URL}}`** | `wechat_article.py` |

**为什么 wechat_article 不是 daily_report 的 re-skin:**
- 字数差 3 倍(长文才有微信生态的转化力)
- 视角差(微信公众号要"我亲眼看到一个赚钱机会",日报要"客观简报")
- CTA 形态不同(公众号靠文末二维码 + 微信号 + 知识星球,日报靠链接)

### 微信公众号生成器:`backend/app/services/content_generator/wechat_article.py`

继承通用 `ContentGenerator` ABC,`name="wechat_article"` / `channel="wechat_article"` / `format="markdown"`。运行流程:

```
Opportunity + ResearchReport + LLMProvider
                │
                ▼
      llm.complete_json(system, user, max_tokens=4096)
                │
                ▼
      _extract_text  →  raw markdown
                │
                ├── _enforce_image_placeholders()    # 每节配 1 张图占位符
                └── _enforce_cta()                    # 强制追加三件套,不重复追加已存在的
                │
                ▼
      GeneratedContent(metadata={
          char_count, cta_placeholders, image_placeholders,
          read_minutes, title_truncated,
      })
                │
                ▼
      Notification(channel="wechat_article", payload={...})
```

**为什么强制 CTA(不信任 LLM):**
公众号 editor 流程 = LLM 写正文 → 人工贴二维码/微信号/链接 → 公众号后台配图 → 发布。三件套永远必须存在,所以在生成器层强制追加。`_enforce_cta` 已包含去重逻辑(LLM 已包含全部 3 个占位符就不重复)。

**字数软警告:**
`char_count < 1500` 时输出 `wechat_article_too_short` warning,**不 raise**。短文也能用,只是运营可能想重跑。

### 5 个新能力

#### 1. `/content/generate` 接通 `generators` 字段

之前 schema 注释里写了但代码不读的 bug:

```bash
curl -X POST http://localhost:8000/api/internal/content/generate \
  -H "X-Radar-Webhook: $WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"opportunity_ids":[1,2,3], "generators":["wechat_article"]}'
```

合法 generator 名单实时从 `get_registry().names()` 读(Phase 8 共 4 个:`daily_report` / `xianyu_product` / `xiaohongshu_post` / `wechat_article`)。未知 generator → 422 + 列出 allowed:

```json

 "unknown": ["nope"],
 "allowed": ["daily_report", "wechat_article", "xiaohongshu_post", "xianyu_product"]}
```

**不传 `generators` = 跑全部**(向后兼容 n8n cron)。

#### 2. `/content/by_opportunity` 加 `?channel=`

```bash
curl "/api/internal/content/by_opportunity?channel=wechat_article&only_qualified=false"
```

返回结构不变,只是 `content` 字典被裁剪到只剩请求的 channel(其他渠道不返回)。前端 "只看公众号" tab 用这个避免拉全表。

响应里同时带 `channel_published: {"wechat_article": "2026-08-28T..."}`,前端用来画 ✓/○ 状态点。

#### 3. `/content/regenerate/{opp_id}` — 单条重跑

```bash
curl -X POST http://localhost:8000/api/internal/content/regenerate/42 \
  -H "X-Radar-Webhook: $WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"generators":["wechat_article"], "delete_previous": false}'
```

- 默认 `delete_previous=False` → **append 模式**(新 Notification 追加,历史保留)
- `enrich=False` → 跳过 LLM 重新富化(已经富化过,省 token)
- 404 兜底
- 同样支持 `generators` 白名单校验

**为什么默认 append 不覆盖:** 运营对 LLM 输出不满意时 100% 需要的 workflow 是"重跑几次,挑最好的那条发"。Append 让运营能看到历史。

#### 4. `/content/export` — 批量导出

```bash
# Bundle:1 个 opp 1 个文件,运营拖入公众号编辑器
curl -X POST http://localhost:8000/api/internal/content/export \
  -H "X-Radar-Webhook: $WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"format":"bundle", "channels":["wechat_article"], "only_qualified":true}'

# CSV:Excel 友好
curl -X POST http://localhost:8000/api/internal/content/export \
  -H "X-Radar-Webhook: $WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"format":"csv", "limit":50, "only_qualified":true}'
```

3 种格式:

| 格式 | Content-Type | 用途 |
|---|---|---|
| **csv** | `text/csv; charset=utf-8` | Excel 统计 / 后处理 |
| **json** | `application/json; charset=utf-8` | ETL / 二次处理 |
| **bundle** | `application/json; charset=utf-8` | 前端 `fetch → Blob → URL.createObjectURL` 触发浏览器下载,运营拖进公众号编辑器 |

bundle 响应:

```json
{"exported_at": "2026-08-28T...",
 "files": [
   {"filename": "ai-customer-service-wechat_article.md",
    "content_type": "text/markdown; charset=utf-8",
    "content": "# 我用 14 天..."},
   ...
 ]}
```

filename 规则:`{slug}-{channel}.{md|json}`。Markdown 渠道 → `.md`,xianyu 是 JSON → `.json`。

| 改动 | 位置 |
|---|---|
| 4 个 channel tab(全部 / 飞书 / 闲鱼 / 小红书 / 公众号) | `ContentCenter.tsx` 顶部 |

| `lib/api.ts` 加 4 个 client:`fetchContentCenter(channel?)` / `markChannelPublished` / `regenerateContent` / `exportContent` | `lib/api.ts` |

#### 批量导出交互流程

1. 勾选若干 ContentPieceCard(每张卡片左上角的 checkbox)
2. 点击右上角 "导出 ▾" 下拉,选 csv / json / bundle
3. 前端 `fetch → Blob → URL.createObjectURL` 触发浏览器下载
4. 运营把 `.md` 文件直接拖入公众号编辑器 / 闲鱼商品页 / 小红书后台

#### "重跑" 按钮

触发 `POST /content/regenerate/{opp_id}` 的 append 模式,完成后:
- Toast 提示 "已重跑 N 个渠道"
- 自动重新 fetch 当前 tab 的数据,新内容立刻可见

- DRY 重构(`_extract_text` / `_extract_title` 上提 `base.py`)— Phase 9 cleanup pass
- 前端 redesign ContentCenter— 增量修改而非重新设计
- Bitable 内容同步(wechat_article 自动同步到飞书多维表格)— 除非运营明确要求

- 微信公众平台编辑器 API 自动发布 — 公众号只支持人工粘贴,无法程序化发布

### 排查清单

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 公众号生成器 4 段但只有 1-2 张配图占位符 | `_enforce_image_placeholders` 跟 section 数不一致 | 看后端日志里 `wechat_article_too_short` 或 `wechat_article_truncated_at_max_tokens`(后者 Phase 9 加)|
| `by_opportunity?channel=xxx` 返回的 content 是空 dict | 该渠道还没生成 / 没勾对应 generator | 先 POST `/content/generate` with `generators:["xxx"]` |

### 与现有 Phase 1-7 的关系

- **Content Center**:原本只画 3 个渠道的卡片,Phase 8 加 `wechat_article` 第 4 张 + 4 个 channel tab + per-channel 状态
- **`mark_published`**:**空 body 行为不变**(全标),新增 `channel` 字段做 per-channel
- **飞书 Bitable 同步**:不受影响,Phase 7 同步的是 Opportunity 表本身,不会因渠道发布状态而变化

## 五之十、Phase 9 v2.0 — 内容编辑器 + 版本管理

Phase 8 让系统能批量产出 4 个渠道的文案,但 LLM 写出来的内容常常"80% 对、20% 还要再改"。Phase 9 给运营一个"不改 prompt 也能调"的工具:

- **就地编辑**:每张渠道卡片上有一个 **编辑** 按钮,点开是一个 modal,可以直接改标题 / 正文 / 备注
- **版本不丢**:每次保存都生成一条新 `Notification`,原始版本不动。新行的 `payload` 里有 `edited_from_notification_id` + `edit_note`,审计可回溯
- **历史回看**:每张卡片左下角的 **查看历史** 链接打开右侧抽屉,显示这个 (机会, 渠道) 的所有版本(最新在上),每条带 80 字预览 + 备注

### 端点

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/internal/content/{notification_id}/edit` | 把编辑后的内容存为新版本 |
| `GET` | `/api/internal/content/{opportunity_id}/versions?channel=...` | 列出某机会某渠道的所有版本 |

### `POST /edit` body

```json
{
  "title":    "新的标题(可选)",
  "body":     "新的正文(可选)",
  "metadata": { "extra_field": "value" },
  "edit_note": "把数字钩子从 14 天改成 21 天"
}
```

至少 `title` / `body` / `metadata` 三者之一,否则 422。`edit_note` 会进入审计追踪。

### 前端操作流程

1. Content Center → 选某张卡片 → **编辑**
2. 改标题 / 正文 → 写一句备注 → **保存为新版本**
3. toast 提示"已保存为版本 #N",卡片刷新显示新内容
4. 点 **查看历史** → 右侧抽屉列出所有版本,新版本在最上,带 "已编辑" 角标

### 排查清单

| 现象 | 原因 | 排查 |
|---|---|---|
| 编辑后点保存报 422 | `title` / `body` / `metadata` 都为空 | 至少改一个 |
| 卡片只显示最新版本,看不到旧版 | 这是预期,卡片渲染的是最新一条;要看历史用 **查看历史** | - |
| 抽屉显示空 | 该 (机会, 渠道) 还没有 Notification | 先 POST `/content/generate` 跑一次 |
| 保存时报"未找到通知 9999" | 那个 notification 已被删除 | 用 `/content/versions` 看哪些 ID 还活着 |

## 五之十一、Phase 10 v2.0 — LLM-as-judge 质量评分

LLM 写的文案质量参差,运营不可能每篇都读一遍。Phase 10 加了一个"评分机器人",用另一个 LLM 调用给每篇内容打分,5 个维度各 1-10:

| 维度 | 评估内容 |
|---|---|
| `hook_strength` | 开头 100 字是否能抓住读者(数字反差 / 故事场景 / 痛点提问) |
| `cta_naturalness` | CTA 是流畅衔接还是生硬拼接 |
| `data_accuracy` | 是否引用了具体数字 / 价格 / 天数,还是泛泛而谈 |
| `char_count_compliance` | 是否符合该渠道的字数区间 |
| `platform_style_match` | 是否符合该渠道的文体调性 |

总分 = 加权平均(默认等权 0.20),**阈值 6.0**。任何一个维度低于 **4.0** 也算不达标,直接标记 `below_threshold: true`。

### 端点

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/internal/content/{notification_id}/quality` | 单条评分 |
| `POST` | `/api/internal/content/{notification_id}/auto_improve` | 评分 + 不达标就重跑(最多 N 次) |

### `POST /quality` body

```json
{ "threshold": 6.0, "persist": true }
```

- `persist: true` → 把评分写进 `Notification.payload.quality_score`,下次 Content Center 直接显示,不再二次调用 LLM
- `threshold` 覆盖本次调用的阈值

### `POST /auto_improve` body

```json
{ "threshold": 6.0, "max_attempts": 2, "delete_previous": false }
```

行为:
1. 评分源 Notification
2. 如果 `below_threshold` 且 `attempts_used < max_attempts` → 重跑同一个 generator,产生新 Notification
3. 重新评分,直到达标或用完 attempts
4. `delete_previous: true` → 删掉这条 (opportunity, generator) 的其它 Notification,只保留最终通过的那条(默认 `false`,append 模式)

### 前端操作流程

1. Content Center → 选某张卡片 → 顶部会显示 **🎯 评分** 按钮(未评过)或一个绿色 / 橙色 **X.X** 小药丸(评过)
2. 点 **🎯 评分** → 弹 toast "X.X ✓" 或 "X.X · 低于阈值"
3. 橙色药丸 → 旁边出现 **自动重跑** 按钮 → 点一次评分 + 重跑,直到通过或 2 次
4. 鼠标悬停在药丸上 → tooltip 显示 5 个子分 + 一句话理由

### 排查清单

| 现象 | 原因 | 排查 |
|---|---|---|
| 评分按钮一直是灰色 | 该卡片还没有 content 生成 | 先跑 `/content/generate` |
| 评分为 5.0 文字"评分服务异常" | LLM 调用失败 | 看后端日志 `content_scorer_llm_failed`;不会触发自动重跑(避免循环成本) |
| 自动重跑后内容没刷新 | 新 Notification 是另一条 | 直接刷新页面,前端 fetch 时取最新 |
| 评分 LLM 调用贵 | 一次最多 400 token,几毛钱 | 调 `persist: true` 后下次免调 |

## 五之十二、Phase 11 v2.0 — 一键发布(基础设施)

4 个渠道的文案都生成了,但发布到平台还得手动复制粘贴。Phase 11 把"发布"抽象成一个 `Publisher` 接口,每个渠道一个子类。当前 4 个平台都是 **stub**——需要凭据(微信公众号 / 小红书蒲公英 / 闲鱼开放平台 / 飞书 App)的部分都是返回 `skipped: true` + 友好的错误提示。

### 端点

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET`  | `/api/internal/publish/channels` | 列出已注册的平台 + 哪些已配置凭据 |
| `POST` | `/api/internal/content/{notification_id}/publish` | 单条发布 |
| `POST` | `/api/internal/content/batch_publish` | 批量发布 |

### 各平台需要的环境变量

| 平台 | 渠道 key | 必需环境变量 |
|---|---|---|
| 微信公众号 | `wechat_article` | `WECHAT_MP_APP_ID` + `WECHAT_MP_APP_SECRET` |
| 小红书蒲公英 | `xiaohongshu` | `XHS_PGY_TOKEN` + `XHS_USER_ID` |
| 闲鱼开放平台 | `xianyu` | `XIANYU_APP_KEY` + `XIANYU_APP_SECRET` + `XIANYU_ACCESS_TOKEN` |
| 飞书 App | `feishu` | `FEISHU_APP_ID` + `FEISHU_APP_SECRET` |

未配齐的端点返回 `success: false, skipped: true, error: "未配置凭据..."`,不是 bug,是 hint。

### `POST /publish` body

```json
{ "channel": "wechat_article", "mark_published": true }
```

- `channel` 不传 → 用 Notification 自己的 channel
- `mark_published: true` → 成功后写 `opp.channel_published[ch]` + flip `content_status='published'`

### 前端操作流程

1. Content Center → 卡片右上角只有配置了凭据的渠道才会出现 **🚀 一键发布** 按钮
2. 点按钮 → 后端调用 Publisher → 成功的话 toast "已发布 · media_id",卡片 ✓
3. 未配置凭据的渠道根本不显示按钮(避免 422 报错骚扰);要看所有平台的状态用 `GET /api/internal/publish/channels`

### 排查清单

| 现象 | 原因 | 排查 |
|---|---|---|
| 卡片没有 🚀 一键发布按钮 | 该渠道 Publisher 未配置凭据 | 跑 `GET /api/internal/publish/channels` 看 `unconfigured` 列表 |
| 一键发布返回 502 | 凭据配齐了但 API 调用失败 | 看后端日志的 `publisher_unhandled_exception`;可能是 token 过期 / 平台限流 |
| 一键发布成功但 `content_status` 没 flip | `mark_published: false` 或接口调用失败 | 检查 body 里 `mark_published` 默认值 |
| 想恢复成人工粘贴 | 把对应 env var 从 `.env` 删了重启即可 | - |

## 六、怎么手动触发一次完整流程

最快的方法是直接调后端 API:

```bash
# 触发完整发现 → 推送流程(从发现到 Telegram)
curl -X POST http://localhost:8000/api/internal/discovery/run \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"sources": ["github","reddit","hackernews","producthunt","rss","youtube"]}'

curl -X POST http://localhost:8000/api/internal/research/run \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \

# 立即推送今日摘要到 Telegram
curl -X POST http://localhost:8000/api/internal/notifications/digest/send \
  -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" \
  -d '{"max_entries": 5, "min_score": 70.0}'
```

可用端点:`/discovery/run`、`/clustering/run`、`/screening/run`、`/scoring/run`、`/research/run`、`/notifications/digest/send`

或者直接在 n8n 面板里点 `manual-pipeline` 工作流 → Execute Workflow,效果一样。

## 九、故障排除

### "firecrawl health: down" / "browser_use health: down"

**原因**:对应 API key 没填、过期、或被代理拦截。

**检查**:
```bash
# 直接 curl 测试连通性
curl -H "Authorization: Bearer $FIRECRAWL_API_KEY" https://api.firecrawl.com/v1/health
curl -H "X-Browser-Use-API-Key: $BROWSER_USE_API_KEY" https://api.browser-use.com/api/v2/tasks -X POST -d '{"task":"test"}' -H "Content-Type: application/json"
```

**修法**:
- 检查 `.env` 里的 key 是否正确
- 如果用了代理,确认代理开着(`export https_proxy=...`)
- 系统会自动降级到下一个 provider,不影响整体运行

### Telegram 没收到推送

**检查 4 件事**:
1. 你和机器人**说过至少一次话**(发 `/start`)
2. `TELEGRAM_BOT_TOKEN` 和 `TELEGRAM_CHAT_ID` 在 `.env` 里填对了
3. 后端日志里有没有 `telegram_send_failed`
4. 测试推送:```bash
   curl -X POST http://localhost:8000/api/internal/notifications/test \
     -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" -d '{}'
   ```

### 飞书没收到卡片

**检查 5 件事**:
1. `.env` 里 `FEISHU_WEBHOOK_URL` 是不是 `https://open.feishu.cn/open-apis/bot/v2/hook/` 开头
2. 群机器人的"加签"开关 和 `FEISHU_WEBHOOK_SECRET` 是否一致(都开 / 都不开)
3. 后端日志里有没有 `feishu_send_failed`,看具体 `error`
4. 测试推送(不需真有飞书 webhook,会走 mock 记录):```bash
   curl -X POST http://localhost:8000/api/internal/feishu/digest/send \
     -H "X-Radar-Webhook: <你的 APP_SECRET_KEY>" -d '{"limit":3,"window_hours":null}'
   ```
5. 加签算法:签错的话飞书会返回 `StatusCode: 230001 / 230002`,看 `app/services/feishu/base.py:sign_feishu_payload` 对照

### n8n 工作流显示 401

API key 没填对。在 n8n 面板生成新的,写进 `.env` 的 `N8N_API_KEY`,然后:
```bash
docker compose restart backend
docker compose exec backend python -m scripts.n8n_sync --activate
```

### 后端启动报错 "pydantic_settings.exceptions.SettingsError"

通常是 `cors_allow_origins` 或 `enabled_sources` 这种逗号分隔字段出问题。看错误信息,一般是把列表写成了 JSON 格式而不是逗号分隔。

### 容器反复重启

```bash
docker compose ps                              # 看哪些不健康
docker compose logs backend --tail=50         # 看具体报错
```

最常见 3 个原因:
1. Postgres 还没就绪(等几秒就好,depends_on 已配)
2. `.env` 里某个必填字段没填
3. 端口被占用(改 `docker-compose.yml` 里的 ports)

### 想完全清空从零开始

```bash
docker compose down -v              # 删容器 + 删 volumes(包括 Postgres 数据)
rm -rf backend/backups/*.sql        # 清备份
make docker-up                      # 重新启动
```
